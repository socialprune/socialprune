# Backlog Management Rule

> **MANDATORY FOR ALL `.kilo` roles IN THE CURRENT REPO / ACTIVE SHELL**
> Deferral must stay honest, explicit, and outside the active task boundary.
> **Version:** 1.0.1
> **Updated:** 2026-04-25

---

## Constitutional Minimum

The backlog exists to track legitimate later work, not to excuse incomplete current work.

---

## Hard Laws

1. The backlog is not a same-scope escape hatch.
2. Work required to satisfy the current task boundary may not be labeled deferred.
3. Deferral is allowed only when value, priority, or prerequisites genuinely support doing the work later.
4. Deferred work must be captured as an explicit backlog entry, not a narrative handwave.
5. If deferral reasoning is weak, vague, or convenience-driven, the default action is to finish the active task instead.
6. Thin constitutional guidance stays here; detailed scoring and evaluation procedure belong in skill space.

---

## Required Behaviors

### Before deferring work
- check whether the work is required to complete the user's current requested outcome,
- check whether the work comfortably fits the active scope and quality bar,
- and treat "can finish now without violating scope" as implement-now, not backlog.

If a threshold, bar, gate, or promotion criterion is the reason for deferring, locate it in a named authority and quote it first. A constraint that cannot be cited is a preference, not a rule, and may not reduce scope. Check the repo-local backlog and lesson archive for a prior correction before repeating a disposition, because a correction already written about the same reasoning outranks that reasoning.

### When deferral is valid
- use explicit backlog capture in `docs/BACKLOG.md`,
- state what is being deferred,
- state why it is not part of the current task boundary,
- and state the trigger or condition that would make it worth doing later.

### When deferral is invalid
Do not call work deferred when it is actually:
- acceptance criteria for the current task,
- cleanup or wiring needed for the same task to be honestly complete,
- a small same-scope fix being parked to avoid finishing properly,
- or a missing step that only became visible because the current task was examined carefully.

### Decision discipline
- Use `yagni-evaluation` when the value or timing is genuinely uncertain.
- Do not use YAGNI framing to dodge already requested, already needed, or already reachable work.
- In the current repo / active shell, backlog entries are planning records for later value, not operator cover for under-execution now.

## Anti-Rationalization Guard

Treat these as deferral warning signs:

- "good enough for now"
- "can be future work"
- "I'll just mention it as a follow-up"
- "the backlog can hold the rest"

If the only reason to defer is convenience, fatigue, or narrative momentum, deferral is not honest.

---

## Failure Rule

If same-boundary work is parked as backlog, or a supposed deferral is not recorded as an explicit backlog item with real later-trigger logic, backlog management has failed.
