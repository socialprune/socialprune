# S1: Streaming ZIP import in a browser worker

## Question

Can the real web importer read 100,000 generated X items, retain them on the page, handle a ZIP64 archive larger than 4 GiB without loading its media entries, and release an interrupted import promptly?

On this machine it imported all 100,000 items in each of three browser runs. The ZIP64 run returned the same count. Abort acknowledgement took 49.6 ms after the page requested cancellation at roughly half the item count. These observations cover the generated inputs and Chromium build below, not every export or device.

## Inputs and method

M1 uses the X lane's generator with count 100,000 and seed 1. The ZIP measured 6,236,036 bytes. Its tweet file held 101,379,677 uncompressed bytes and its note file 1,624,648 bytes, approximately 1,014 bytes per generated tweet. The generator includes replies, quotes, reposts and 1,000 longer posts with matching note records. The final M1 generation took 3.328 seconds. Inputs are invented, not copies of a real export.

M2 composes that same `largeEntries` iterator with five seeded xorshift32 padding streams under `data/tweets_media/`. Each produces 896 MiB in chunks of at most 1 MiB. `writeZipFile` uses `zip64: true` and per-entry `level: 0` for the padding, so no complete media entry is held in memory. The final archive measured 4,703,857,916 bytes. Its central directory begins at byte 4,703,856,929, beyond the 32-bit offset range. Independent header readback found the ZIP64 end record and locator, and method 0 with compressed and uncompressed sizes of 939,524,096 bytes for every padding entry. Generation and header verification took 35.618 seconds.

The app sends Files to its module worker. Core opens the ZIPs and streams JSON through both adapters. The worker posts batches of 1,000 items; the page retains every received item in its main-thread array. A terminal summary is sent only after `archive.close()`. Wall time starts immediately before the client posts the import request and ends when the page receives that summary. It excludes ZIP generation, file selection, browser startup and build time.

Memory is an OS measurement, not a JavaScript heap estimate. CDP `SystemInfo.getProcessInfo` identifies the fresh browser's processes before import. The sampler sums Windows `PrivateMemorySize64` and `WorkingSet64` for those PIDs, including the renderer hosting the page and worker, browser, GPU and network service. The final inventory check rejects a row if a new process escaped sampling. All five rows had the same four process identities before and after import.

The sampler requests a 100 ms interval. Actual mean intervals ranged from 146.9 to 161.1 ms and the longest gap was 323 ms. Peaks include file selection, import and a 500 ms settling window, extended to five seconds after abort. Shorter peaks between samples can be missed. Working sets include shared resident pages and Chromium overhead; their sum can count shared pages more than once. Private bytes are the more useful comparison between M1 and M2 here. No forced garbage collection or OS working-set trim was used.

A test-only Playwright probe wraps the worker's native `Blob.slice` without changing returned bytes and records requested ranges. M1 requested 12,483,772 ZIP bytes in 13 reads; the note-matching path reads the tweet entry twice. M2 requested 12,484,590 bytes in 20 reads. The M2 ranges did not overlap any padding payload. It read the data entries at offsets greater than 4 GiB and left the padding unopened.

The context records actual browser requests and failed requests, page exceptions and document/worker CSP events. The runner does not route requests or replace `fetch`. No external-origin request, failed request, page exception or CSP violation was observed in the accepted rows.

## ZIP footer boundary found during development

A preliminary media-last ZIP64 trial imported 100,000 items in 10.2323 seconds, but the zero-media-byte assertion failed. Recorded ranges identified one 65,557-byte footer-search read at the end of the archive. It overlapped the last media payload by 64,578 bytes; no media entry was extracted. The final trial puts padding before the generated data, so the same footer search lands in data already needed for import.

The final zero-overlap result therefore applies to that measured layout. For arbitrary exports, the ZIP directory search can touch a small media tail even when the adapter never opens media. The importer does not promise that no byte belonging to media is ever read. The range audit remains fail-closed instead of treating footer overlap as zero. Earlier full runs are diagnostic evidence, not replacements for the final table.

## Browser proof and CSP

`pnpm test:e2e` passed 53 tests against the production build through preview, in 38.0 seconds in the final fixture run. The tests discover variants through `listFixtureVariants`, require a populated set and at least one eligible import per platform, and exercise all variants whose expected status is not `unknown-format`: 21 X and 29 Instagram variants in this snapshot. They compare status, platform, accounts, variant, export creation time, item count, complete diagnostics and sorted item IDs with each independent `expected.json`.

Every fixture import observes context requests, including workers and service workers if present, plus page request and failure events. No service worker is installed by this Phase 1 page. The origin audit, page error checks and document/worker violation checks passed without request interception. The X injection fixture returned `partial`; `globalThis.__pwned` was undefined in the page and its real worker. The abort test uses 8,000 generated items, checks the raw aborted receipt and absence of later item batches, and imports another fixture afterwards. Unit tests cover close-before-summary, cancellation, stale messages, completion/cancellation races and retry after a worker crash.

The shipped HTML contains no inline script and uses this meta policy:

```text
default-src 'none';
script-src 'self'; worker-src 'self'; connect-src 'none';
style-src 'self'; img-src 'none'; font-src 'none'; object-src 'none';
base-uri 'none'; form-action 'none'
```

Neither JavaScript string evaluation nor WASM compilation permission is included. ZIP decompression runs inside the app-owned worker through native `DecompressionStream`, with zip.js nested workers disabled. The document meta policy does not impose a worker response policy. GitHub Pages cannot supply that response header; the later service-worker approach from [S3](S3.md) must deliver and verify the worker's own CSP. Observed absence of worker network requests is not proof that a worker response CSP is already shipped.

CI installs Chromium with system dependencies and runs the fixture e2e suite after build. It does not run these large measurements.

## What the trial did not prove

This tested one desktop, one headless Chromium build, generated X data, four complete browser imports and one interrupted import. It did not test Firefox, Safari, phones, real export deviations, millions of items, storage persistence, browser restarts, exhaustive archive corruption, every ZIP64 layout, encrypted exports or GitHub Pages deployment/base-path behavior. Real exports and signed-in profiles were not used. The worker's imported file data is parsed, not executed; the injection test exercises one specific executable-assignment rejection case, not every possible malicious archive.

Sampling can miss brief peaks, and Windows private bytes are committed process memory rather than live object size. The machine was not isolated from all other work, OS caching was not reset, and three runs do not describe a latency distribution. Abort was measured after 51 batches, not at every decompression or detection boundary. Post-abort memory did not return to baseline during the five-second observation.

## Rerun

Run from the repository root with the pinned workspace dependencies installed and Chromium available:

```powershell
pnpm --filter @socialprune/web exec playwright install chromium
pnpm test:e2e
pnpm measure:g1
```

`measure:g1` generates both ZIPs in a unique trial directory below `%LOCALAPPDATA%\Temp\kilo\phase1-foundation\s1`, builds the app, starts preview on port 4175, runs M1 three times, M2, M3 and M4, and writes `results.json`. It closes each browser/context, stops its memory sampler and preview, and removes only its generated archives, including on a failed trial. Allow at least 5 GiB of free temporary storage. The OS sampler currently requires Windows. Playwright e2e uses a separate preview on port 4180; the Linux CI run was not exercised in this spike.

`pnpm measure:g1 --probe-memory` runs a 1,000-item wiring probe. `--only-m1` omits ZIP64, `--only-zip64` omits the three M1 rows, and `--without-node` omits M4. Those partial runs do not satisfy the full table. The readback utility accepts only an explicit aggregate report:

```powershell
node apps/web/scripts/readback-s1.ts "<printed results.json path>"
```

The final raw trace for this record is `%LOCALAPPDATA%\Temp\kilo\phase1-foundation\s1\trial-0e259N\results.json`. It contains aggregate timing, process memory and ZIP byte ranges, not item text. No raw trace, browser profile or large ZIP is delivered in Git.
